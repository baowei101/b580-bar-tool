# 任务：编写一个 Linux 下启用 PCIe Resizable BAR 的运维脚本

## 背景

一台 x86 Linux 服务器（Ubuntu，内核 7.0.0-38，无 IPMI/无带外管理）上装了 Intel Arc B580 显卡（12 GB 显存）。
显卡驱动 `xe` 只能访问 512 MB 的显存窗口（BAR2），远小于实际 12 GB，导致大模型推理时显存访问受限。

需要写一个 bash 脚本：通过 PCIe Resizable BAR 扩展能力把 BAR2 从 512 MB 扩到 16 GB，并让内核重新枚举
PCIe 根端口以接受这个尺寸。

## 已验证的环境事实（直接采用，不要再猜）

### PCI 拓扑

```
0000:00:02.0  pcieport      PCIe 根端口 (bus 02-05)
  └─ 0000:02:00.0  pcieport  显卡板载 PCIe switch 的上游端口 (bus 03-05)
       ├─ 0000:03:01.0 pcieport  下游端口 (bus 04)
       │    └─ 0000:04:00.0  xe            目标 GPU（Arc B580）
       └─ 0000:03:02.0 pcieport  下游端口 (bus 05)
            └─ 0000:05:00.0  snd_hda_intel  HDMI 音频
```

根端口 `00:02.0` 的子树下**只有这张显卡**，没有其他设备。

### ReBAR 扩展能力寄存器实测值（GPU 0000:04:00.0）

扩展能力结构位于配置空间偏移 `0x420`：

| 偏移 | 值 | 含义 |
|---|---|---|
| `0x420` | `0x40010015` | ECAP header：next=0x400, version=1, ID=0x0015（Resizable BAR） |
| `0x424` | `0x0007f000` | Capability 寄存器 |
| `0x428` | `0x00000922` | Control 寄存器 |
| `0x42c` | `0x00000000` | Status 寄存器 |

字段解析规则：

- **Control 寄存器**（`0x428`）：
  - `bits[2:0]` = BAR Index，当前值 2，表示操作的是 BAR2
  - `bits[13:8]` = BAR Size 字段 N，对应实际大小 `2^(N+20)` 字节
  - 当前 `0x922` → N=9 → `2^29` = 512 MB（与实测一致）
  - 目标 N=14 → `2^34` = 16 GB
  - 写这个寄存器时只能改 `bits[13:8]`，`bits[2:0]` 及其他位必须原样保留

- **Capability 寄存器**（`0x424`）：`bit(4+N)` 置位表示支持大小 `2^(N+20)`
  - 当前 `0x0007f000` → bits 12..18 置位 → 支持 N=8..14 → 256 MB / 512 MB / 1 GB / 2 GB / 4 GB / 8 GB / 16 GB
  - 因此本卡可达到的最大 N = 14（16 GB）

### 内存与窗口现状

- 根端口 `00:02.0` 的 prefetchable 窗口：`c0000000-e07fffff`，**520 MB，且位于 32-bit 地址空间**
  （520 MB = switch 上游 BAR0 8 MB + GPU BAR2 512 MB）
- 系统 64-bit MMIO 空间非常充裕，有两个各约 1 TB 的区间：
  - `20000000000-2ffffffffff`（PCI Bus 0000:00）
  - `30000000000-3fffffffff`（PCI Bus 0000:80）
- 内核命令行**已经带 `pci=realloc`**，但启动时没有扩大根端口窗口（因为对现有 512 MB 的 BAR "够用"）
- 驱动 `xe` 在每次启动时会自己尝试 `resize bar from 512MiB -> 16384MiB`，失败日志为：
  ```
  BAR 2 [mem size 0x400000000 64bit pref]: can't assign; no space
  BAR 2 [mem size 0x400000000 64bit pref]: failed to assign
  BAR 2 [mem 0xc0000000-0xdfffffff 64bit pref]: old value restored
  Failed to resize BAR2 to 16384MiB (-ENOSPC). Consider enabling 'Resizable BAR' support in your BIOS
  Small BAR device
  ```
- 即：**内核想给 16 GB，但根端口的窗口不肯长大**。

### 已有的技术方向（原理公开，可自由使用）

把 GPU 的 ReBAR Control 寄存器 size 字段改写为目标值，然后让内核重新枚举该根端口
（先让驱动解绑、把根端口从内核设备树中移除、再触发重新扫描），内核便会按新的尺寸重新分配窗口。

## 必须实现的子命令

| 子命令 | 行为 |
|---|---|
| `status` | 只读。打印当前 BAR2 大小、可用最大值、根端口窗口、驱动绑定情况、判定结论 |
| `plan` | **默认子命令**。dry-run，逐条打印将要执行的每个动作及其预期结果，不产生任何修改 |
| `apply` | 真正执行 |
| `rollback` | 把 size 字段恢复到脚本启动前记录的初始值 |

## 必须由你自己设计对策的风险

以下几点任务书不提供解法，需要你在脚本里自行设计并实现：

1. **根端口下若有其他设备**，移除根端口会把它们一起摘掉。脚本必须检测并在这种情况下拒绝执行。
2. **移除 + 重扫之后 BAR2 可能仍然分不到地址**（窗口不够）。必须能检测出来并回滚。
3. **重新扫描过程可能让整个内核挂死**。这台机器没有 IPMI，一旦挂死只能到机房按电源键。
   请思考：能否把风险窗口缩到最小？能否在每一步之前留下足以事后判断的日志痕迹？
   能否设计成"即使中途死机，重启后也是干净的"？
4. **回滚本身也可能失败**（回滚后 BAR2 依然分不到地址，GPU 完全不可用）。需要兜底考虑。
5. **GPU 上正在跑推理任务时被移除会出问题**（DMA 在途）。脚本应如何处理？
6. **幂等性**：重复执行 `apply`，或先 `apply` 再 `apply`，不应造成破坏。
