# b580-bar-tool.sh 独立评审报告

- 被审文件：`D:\2\b580-bar-tool\b580-bar-tool.sh`（691 行，bash）
- 版本标注：v1.1.0（第 30 行）
- 评审立场：Linux PCI 子系统 / PCIe 配置空间 / Resizable BAR（ECAP ID 0x0015）
- 评审方式：逐段静态审查，不执行、不修改任何文件
- 结论标记：**[确认]** = 有可验证依据（行号 + 语言/内核行为）；**[可疑]** = 依赖硬件或内核版本，无法静态定论

## 0. 先说结论形态

脚本整体结构（落盘 STEP 痕迹、unbind→write→remove→rescan→verify→rebind、演练与实做分离）设计思路是对的，
寄存器偏移与位掩码与给定事实一致。但**真正决定成败的三件事**——「窗口够不够」「失败了能不能回得来」「寄存器读失败怎么判」——
恰好是脚本处理得最弱的三处。下面是逐项依据。

## 1. 寄存器读写与位操作

### 1.1 确认正确的部分

| 项 | 行号 | 结论 |
|---|---|---|
| `REG_CAP=0x04` / `REG_CTL=0x08` / `REG_STA=0x0C` | 32-34 | 与 ReBAR ECAP 布局一致（header 在 +0x00） |
| `SIZE_MASK=0x3F00`、移位 8 | 35、183、323、502、667 | 0x3F00 = bits[13:8]，与给定 Control=0x922 → size=9 吻合 |
| 保留 bits[7:0]（含 BAR index） | 323 | `(orig & ~SIZE_MASK) \| (n<<8)` 不破坏 BAR index 与保留位，正确 |
| `ECAP_HINT` 先验再回退扫描 | 123-127 | 顺序正确 |
| 写后回读校验 | 335-339 | 正确且必要 |
| `setpci` 只用 `.l` | 173-181 | 正确（pciutils 无 `.d`） |
| 十六进制偏移换算 | 175-177 | `$((ECAP_OFF + REG_CAP))` 对 `0x420` 字符串与十进制两种形态都能正确求值（bash 算术递归解析 0x 前缀） |
| `bar2_mb` 取 `resource` 第 3 行 | 201 | 正确，第 1 行是 BAR0，第 3 行即 BAR2 |

### 1.2 缺陷

**[确认-中] D-01：`ctl_baridx` 只用于显示，从不校验它是否等于 2**
- 行号：36、184、446；写入点 334 之前没有任何 `BARIDX == 2` 的断言。
- 脚本写的是「ECAP 基址 + 0x08」这一条 entry，隐含假设「第 0 条 entry 就是 BAR2」。本卡恰好成立，
  但代码层面没有守住这个假设。若 ECAP 有多条 entry（每 8 字节一条：Cap+Ctrl），写错 entry 会去改另一个 BAR 的 size。
- 依据：184 行的 `ctl_baridx` 全文仅被 446 行 `log INFO` 调用一次，返回值从未进入任何条件判断。

**[确认-中] D-02：Capability / Control 读取为空时被静默当作 0**
- 行号：436-437（`cmd_status`）、495-498（`cmd_plan_or_apply`）。`cap_read`/`ctl_read` 都带 `2>/dev/null`（175-176），
  失败时返回空串；`hex2dec ""` 在 78-79 行显式 `echo 0`。
- 后果链（可推演）：
  - `cmd_status` 453 行：`cur_n(0) -ge max_n(0)` 成立 → 打印 **「BAR2 已是本卡最大尺寸，无需处理」**（假阳性）。
  - `cmd_plan_or_apply` 530 行：`0 -ge 0` 成立 → **「BAR2 已是目标尺寸，幂等退出」**，什么都不做却报成功。
- 即：只要 ECAP_OFF 被误判或 setpci 读失败，脚本会以「成功」的姿态静默退出。这是最典型的"漏判导致误判成功"。

**[确认-低] D-03：`max_supported_n` 只扫 bit 4..28，漏 N=25..27**
- 行号：190 `for bit in $(seq 4 28)`。Capability 的 supported 位域是 bits[31:4]，理论上 N 可到 27。
- 实际影响为零（N=14 已够），但属实现不完整。

**[确认-低] D-04：`ecap_find` 用暴力全扫描代替 ECAP 链遍历**
- 行号：121-129。对 0x100..0xFFC 每 4 字节判低 16 位 == 0x0015，**任何** 4 字节对齐、低半字恰为 0x0015 的数据都会被认定为 ReBAR ECAP。
- 一旦误判，`ECAP_OFF + 0x08` 就指向一个未知寄存器，334 行的 `ctl_write` 会往那里写 `0x00000e22`。
- 概率低（hint 0x420 优先命中），但正确做法应是沿 `next capability pointer`（bits[31:20] of ECAP header）遍历。

**[可疑-低] D-05：`bar2_mb` 对 ≥2^63 的地址会溢出**
- 行号：205-206。`s=$((start))` 用 bash 有符号 64 位算术；若 BAR 基址 ≥ 0x8000000000000000，`e > s` 判为假 → 输出 0 → 被 366-369 行当作「BAR2 未分配」。
- 真实硬件 MMIO 通常 < 2^48，此条实际不会触发，仅登记。

## 2. 前置检查（preflight）

### 2.1 已有的、做得对的
- 225-231：`pci=realloc` 校验（`grep -qw` 对含 `=` 的模式工作正常）。
- 240-247：子树设备白名单（0x0604 桥 / 0x0403 音频 / GPU 自身），防误伤异物。
- 250-261：`fuser` 检测 GPU 节点占用。
- 470-480：`fuser` 缺失与无看门狗告警。

### 2.2 缺陷

**[确认-高] D-06：完全没有校验根端口窗口容量是否装得下 16GB**
- 行号：209-216 定义了 `root_window_mb`，235 行在 preflight 里**只 log 不比较**；
  450 / 512 也只是打印。全文没有任何一处把窗口 MB 与目标 MB（16384）做比较。
- 后果：即使 prefetchable 窗口只有 512MB/1GB，apply 也会照常往下走，直到 370-373 行才发现"被降级分配"，
  然后走进 D-08 那个**无效的回滚**。
- 这是"前置检查是否足够"这一问里最大的缺口：脚本把最可能致命的判断推迟到了最危险的步骤之后。

**[确认-中] D-07：不校验目标 N 在 Capability 位图中是否真的置位**
- 行号：500 只判 `target_n <= max_n`，不判 `(cap >> (4+target_n)) & 1`。
- 例：Capability=0x0007f000 支持 N=8..14；若传 `--size 10`，`10 <= 14` 通过，但 bit(14) 未置位 → 写入非法 size，设备行为未定义。
- 同样的洞也影响 `cmd_rollback` 的默认 N=8（见 D-11）。

**[确认-中] D-08：`cmd_rollback` 完全跳过 preflight**
- 行号：654-668，`cmd_rollback` 只调 `need_root` + `gather`，**没有** `preflight`。
  因此不检查 `pci=realloc`、不检查子树异类设备、不检查 GPU 是否被进程占用。
- 后果：可以在有推理任务跑着的时候触发 remove+rescan（`rollback_to` 396 行会 remove 根端口）。

**[确认-高] D-09：`ROOT_BDF` 为空时 `subtree_devices` 会枚举整机所有 PCI 设备 —— unbind 会变成"解绑全机驱动"**
- 行号：149-155。`subtree_devices ""` → `realpath "/sys/bus/pci/devices/"` = `/sys/bus/pci/devices` →
  `grep "^/sys/bus/pci/devices/"` 匹配**每一个** PCI 设备。
- 触发路径：`cmd_rollback`（654）不校验 `ROOT_BDF`；`rollback_to`（388）直接调用 `unbind_leaf_drivers`（278-288），
  后者对子树内每个非桥设备执行 `unbind_one` → 会把网卡、存储、USB 控制器等的驱动全部解绑。
- 触发条件：`detect_root_port`（143-147）的 sed 正则取不到值（例如 GPU 直连根复合体、sysfs 路径形态变化、域号非 4 位）。
  在当前实测拓扑下不会触发，故标 **[确认-高（潜伏）]**：代码里没有任何一处对 `ROOT_BDF` 为空做防护——
  233 行的检查只在 `preflight` 里，而 `cmd_rollback` 根本不调 `preflight`（见 D-08）。
  这两条叠在一起，是一个"低概率 × 灾难性"的组合。

**[可疑-中] D-10：未校验根端口/switch 是否支持 64-bit prefetchable 窗口**
- 16GB 必须是 64-bit prefetchable。脚本只从 `lspci -vv` 抓 `Prefetchable memory behind bridge` 的字面量，
  既不判窗口上限，也不判桥是否支持 64-bit prefetch 译码。C610/Wellsburg 通常支持，故标可疑。

## 3. 执行顺序与失败处理

当前顺序（do_resize，319-378）：
`unbind_leaf_drivers`(329) → `ctl_write`(334) → 回读校验(335-339) → `remove 根端口`(346) → `rescan`(353) → 验证(357-373) → `rebind`(376)

顺序本身合理（先解绑、再改配置、再重枚举），但失败处理有三处硬伤。

**[确认-高] D-11：驱动解绑失败只记 WARN，流程继续**
- 行号：273-274。`echo "$bdf" > .../unbind 2>/dev/null || log WARN "..."` —— EBUSY 时函数仍返回 0。
- 于是 334 行会在驱动仍绑定的状态下写 Control，346 行会在驱动仍绑定的状态下 `remove` 根端口。
  对已绑定驱动的设备做 `pci_remove_bus_device`，轻则 `-EBUSY` 失败，重则驱动侧 UAF/Oops。
- 最小修复：解绑失败应 `return 1`（或至少对 GPU_BDF 本身失败即中止）。

**[确认-高] D-12：写 Control 前未清 Command 寄存器的 Memory Space Enable / Bus Master Enable**
- 全文检索：脚本**没有任何一处读写偏移 0x04 的 Command 寄存器**。
- 规范约定（ReBAR ECN）：改 BAR Size 前应确保该 BAR 不在被访问，推荐先清 MSE/BME；改完需重新 probe BAR（写全 1 再回读）。
- 334→346 这段窗口期里：GPU 的 MSE 仍为 1，BAR2 基址寄存器仍是旧的 512MB base，而 BAR 尺寸字段已变成 16GB。
  由于驱动已解绑、且随后立刻 remove 根端口，实际引爆概率不高；
  但 334 与 346 之间若因任何原因停顿（如 341 行的 `sync` 慢、脚本被 Ctrl-C），设备就处于"译码范围与窗口不匹配的未定义状态"。
- 定性：**[确认]** 规范符合性缺陷；**[可疑]** 是否真会触发故障（取决于设备实现）。

**[确认-中] D-13：无 `trap`/EXIT 兜底**
- 脚本从 334（写 Control）到 353（rescan）之间是"已改配置、尚未重枚举"的不一致态，
  期间若被 SIGINT/SIGTERM 打断或被 OOM killer 杀掉，没有 trap 会尝试回滚。
- 对比：脚本对"内核挂死"这个不可恢复场景反而写得很细（63-67 的 step 落盘 + 412-423 的兜底提示），
  但对"脚本自身被打断"这个可恢复场景没有任何处理。

**[确认-中] D-14：成功判定不校验驱动是否真的回绑**
- 行号：376 `rebind_leaf_drivers` → 299-300 绑定失败仅 `log WARN`；377 无条件 `return 0`。
- 于是 558 行会打印"完成"，而实际上 headless 机器上的 `xe` 可能根本没绑上。

**[确认-低] D-15：`rescan_wait` 不检查 rescan 写入是否成功，重试窗口偏窄**
- 行号：307、313，`echo 1 > /sys/bus/pci/rescan 2>/dev/null` 无状态判断；309 只重试 3 次 × 1s。
  对带 switch 的拓扑枚举是同步完成的，通常够用；但若内核返回 EBUSY 则静默放过，只能靠 359 行兜底。

## 4. 回滚路径

**[确认-高] D-16：回滚在"最可能的失败模式"下完全失效**
- 触发链：370-373（`now_mb != want_mb`，即窗口不足被降级）或 359-362（GPU 未重新出现）→ `return 2`
  → 559-560 `rollback_to "$ctl"`。
- `rollback_to`（380-410）：
  - 387 行：`if [ -e "/sys/bus/pci/devices/$GPU_BDF" ]` 为真时才写回寄存器；
  - 391-393：GPU 不可见时**只打印"无法写回寄存器"**，无任何替代手段；
  - 395-399：随后仍然 remove 根端口 + rescan —— 而设备配置空间里 Control 仍是 16GB，
    rescan 会以同样的 16GB 请求再失败一次；
  - 402-409：`bar2_mb -gt 0` 不成立 → "回滚后 GPU 仍不可用" → `fallback_notice`。
- 也就是说：**回滚函数唯一真正有效的分支（387 写回寄存器）依赖 GPU 可见；而 GPU 不可见恰恰是 16GB 分配失败最典型的后果。**
  回滚在这个场景里退化成"再试一次同样的失败 + 打印断电提示"。
- 脚本对此是诚实的（412-423 明确说要断电重启），但"rollback"这个子命令名给出的保证与实际能力不符。
- 注：若失败形态是"GPU 可见但 BAR2 未分配"（366-369），回滚**是**有效的——387 能写回，这条路走得通。
  所以 D-16 应表述为"对 GPU 掉线这一分支无效"，而非"完全无效"。

**[确认-中] D-17：`cmd_rollback` 无状态文件时默认缩到 256MB（N=8），而不是原 512MB（N=9）**
- 行号：664 `target_n="${TARGET_N:-8}"`。原值是 N=9（512MB），capability 支持 N=8..14。
- 叠加 548 行 `echo "CTL=$ctl" > "$STATE_FILE" 2>/dev/null || true`（写状态失败被静默吞掉），
  或用户从未跑过 apply 就跑 rollback → 结果是把 BAR2 改成 256MB，**比原状更小**，且可能不够 `xe` 用。
- 修复方向：默认取 capability 里置位的最小 N，或直接用当前值兜底而非硬编码 8；STATE_FILE 写入失败应告警。

**[确认-低] D-18：`STATE_FILE` 不记录 BDF / 时间戳**
- 行号：548 只写 `CTL=...`；660-663 读回时不校验这条记录属于哪个设备、是否是本次运行产生的。
  多卡或历史残留场景下会串。

## 5. 幂等性

- **[确认-正确]**：530-533 `cur_n >= target_n` → 幂等退出。apply 成功后重复执行会安全退出。
- **[确认-低] D-19**：幂等判断只看 Control 的 size 字段，不看 BAR2 实际窗口（449/364）。
  若出现"Control 写成功了但窗口是降级的"这种状态，重复 apply 会误判为"已是目标尺寸"退出。
  与 D-02 同属"只看寄存器、不看实际"的取向。
- **[确认-低] D-20**：`STATE_FILE`（47）只在 548 写入，从不清空；成功 apply 后残留，
  之后误跑 `rollback` 会把 16GB 缩回 512MB。这是设计意图，但没有二次确认（`cmd_rollback` 没有 `--yes` 之外的确认交互）。

## 6. `set -uo pipefail` 下的陷阱

脚本用 `set -uo pipefail`（28），**未用 `set -e`**。逐条核对：

**[确认-高] D-21：`shift 2` 失败导致无限循环**
- 行号：103-105（`--gpu`、`--size`、`--log`）。
- bash 行为：`shift 2` 在 `$# == 1` 时打印 "shift count out of range"、返回 1，**且不修改位置参数**。
- 于是 `./b580-bar-tool.sh apply --gpu`（缺值）→ `while [ $# -gt 0 ]`（101）恒真 → `case` 反复命中 `--gpu` →
  `shift 2` 反复失败 → **死循环**，进程永不退出（无 `set -e` 兜不住）。
- 这是可直接复现的确定性缺陷：`bash -c 'set -- --gpu; while [ $# -gt 0 ]; do case $1 in --gpu) shift 2;; esac; done'`。

**[确认-中] D-22：大量关键写操作的失败被吞**
- 273（`unbind`，只 WARN）、307/313（`rescan`，无判断）、396（`remove`，`|| true`）、
  548/553/554（状态与快照，`|| true`）、58/60/65-66（日志与 step，`|| true`）。
- 其中 396 的 `|| true` 尤其值得注意：回滚里 remove 根端口失败被完全忽略，随后仍执行 rescan（398-399）。

**[确认-中] D-23：`local` 与命令替换的组合**
- `local ans; read -r ans`（543）在 `set -u` 下安全（`read` 即使 EOF 也会赋空串，544 判不等 → die，行为正确）。
- 但 `local saved; saved="$(...)"`（661）与 `local rc=0 d cls drv`（223）这种写法在 `set -u` 下依赖后续赋值成功；
  661-662 已有 `[ -n "$saved" ]` 守卫，安全。
- `driver_of`（218）在 readlink 失败时返回空串且**退出码为 0**（`basename ""` 返回 0），
  因此 451 行 `$(driver_of "$GPU_BDF" || echo none)` 的 `|| echo none` **永不生效**，无驱动时打印空而非 "none"。
  **[确认-低]**，仅显示问题。

**[确认-低] D-24：`set -- $size`（214）在函数内重置位置参数**
- `root_window_mb` 内部使用，只影响本函数的 `$1/$2`，不会外泄；但依赖未加引号的单词拆分，且会受 glob 展开影响。
  功能性正确，风格脆弱。

**[确认-低] D-25：`log()` 内 `[ -n "$LOG_FILE" ]`（57）是永真分支**
- `LOG_FILE` 只可能是 45 行的 `/var/log/...` 或 675 行的 `./b580-bar-tool.log`，永不为空 → 该判断恒真，属冗余。

## 8. 最严重的 3 个问题（按风险排序）

### 第 1 位 — 回滚在关键分支失效，且回滚路径本身可能被放大成整机事故
- 依据：387-393（`rollback_to` 在 GPU 不可见时只打印，不写回）+ 395-399（用同样的 16GB 配置再 rescan 一次）+ 402-409（判定失败 → 断电提示）；
  叠加 D-08（`cmd_rollback` 不调 `preflight`）+ D-09（`ROOT_BDF` 为空时 `subtree_devices` 枚举整机 → `unbind_leaf_drivers` 解绑所有非桥设备驱动）。
- 影响：16GB 分配失败最典型的后果就是 GPU 掉线，而这条分支恰好是回滚唯一修不了的场景；
  同时 `rollback` 子命令在没有前置保护的情况下，一旦 `detect_root_port` 失手就可能解绑整机的 PCI 驱动。
- 风险等级：**高**（低概率 × 灾难性 + 高频失败路径 × 无恢复能力）。

### 第 2 位 — 写 Control 前未禁用设备译码，且解绑失败不阻断
- 依据：273-274（unbind 失败只 WARN，返回 0）→ 334（仍写 Control）→ 346（仍 remove 根端口）；
  全文无 Command 寄存器（偏移 0x04）的 MSE/BME 操作。
- 影响：带绑定驱动做 `remove` 是内核侧 UAF 风险；改 size 时 MSE=1 违反 ReBAR 规范的操作序列约定。
- 风险等级：**高**（确认缺陷；触发概率取决于设备与时序）。

### 第 3 位 — 前置检查漏掉"窗口容量"与"Capability 位"两项硬校验，且寄存器读失败被当 0
- 依据：235（`root_window_mb` 只 log 不比较）、500（只比 `<= max_n`，不校验 bit(4+N) 置位）、
  436/495（读空 → `hex2dec` 返回 0）、453/530（0>=0 → 报"已是最大/已是目标，幂等退出"）。
- 影响：① 在窗口明显装不下 16GB 的情况下仍会执行，把风险推迟到 remove/rescan 之后才发现，而失败又落回第 1 位；
  ② 读失败时以"成功"姿态静默退出，是典型的假阳性。
- 风险等级：**高**（直接决定 apply 的成败与可诊断性）。

> 紧随其后（第 4，确定性但影响范围有限）：D-21 的 `shift 2` 死循环——`./b580-bar-tool.sh apply --gpu` 会挂死，
> 不损坏系统，但属于可复现的确定性 bug。

## 9. `apply` 现在能不能安全执行？

**结论：不建议按现状直接执行 `apply`。** 理由分两层：

**A. 演练证据的覆盖面不够。**
已实测通过的 `rehearse` 只证明了「解绑 → remove 根端口 → rescan → 验证 → 重绑」这条链路在本机可行（4 秒、零挂死），
但它**不写 Control**，因此完全没有验证：
1. Control 写入后设备行为是否正常；
2. 16GB 的 64-bit prefetchable 窗口能否在 `pci=realloc` 下真正分配到（这才是 apply 唯一的实质未知项）。
而这第 2 点，脚本恰恰**没有做任何事前判断**（D-06）。

**B. 一旦第 2 点失败，脚本的自救能力为零。**
失败后最可能的形态是 GPU 不可见或 BAR2 未分配，走 `return 2` → `rollback_to`：
- GPU 不可见分支（391-393）无法写回寄存器，只能断电重启（第 1 位问题）；
- 也就是说"失败 → 自动恢复"这条承诺在最需要它的场景下不成立。

**若要执行，建议至少补齐以下 6 项**（均为小改动，不改变整体流程）：
1. `unbind_one` 失败改为致命（273-274），尤其 GPU 自身。
2. 写 Control 前清 Command 的 MSE/BME，rescan 后再恢复（新增几行 setpci）。
3. `preflight` 增加硬校验：`root_window_mb >= 16384`、桥支持 64-bit prefetchable、以及 `(cap >> (4+target_n)) & 1` 置位（209-216 / 500）。
4. `cap_read`/`ctl_read` 返回空立即 `die`，禁止 `hex2dec` 把它当 0（436、495）。
5. `cmd_rollback` 补 `preflight` 并加 `ROOT_BDF` 非空断言（654、380）；`shift 2` 改为先判 `$# -ge 2`（103-105）。
6. 334-353 之间加 `trap`，被中断时自动尝试回滚（D-13）。

**另一个值得先试的更稳路径**（需自行确认当前内核是否支持、是否要求先解绑驱动）：
内核自带的 `/sys/bus/pci/devices/0000:04:00.0/resource2_resize` 接口。
它由内核内部完成 BAR resize 与桥窗口重分配，不需要手写寄存器、不需要 remove/rescan 根端口，
失败时也只返回 errno 而不会把设备搞成不可见状态。若这条内建路径可用，风险显著低于本脚本的手工流程。
（此项为建议，非本脚本缺陷。）
