## 四、三席均报的一条：无 `trap`（审核当时未修，2026-10-28 已补）

三席都认为"remove 与 rescan 之间被中断会留下消失的子树"是缺陷，这个判断**是对的**，
我们也没有找到反驳理由。审核当时的状态是：

- 未修。
- 也**尚未**写入 `NEXT.md` 的"已知未修"清单 —— 这是本文档写就时补记的疏漏。
- 风险实测边界：`remove` 与 `rescan` 之间的窗口在本机是**毫秒级**（`apply` 全程 4 秒，
  其中 remove→rescan 只占很小一段），被 Ctrl-C 恰好打断的概率低，但一旦发生，
  后果是锚点子树消失、需要 `echo 1 > /sys/bus/pci/rescan` 或重启恢复。
- 当时的待办优先级定为 **P0**：理由不是概率，而是后果不可自愈（用户看到的是一块消失的显卡）。

**补修方案（已实施）**：两个脚本都加全局标志 `PCI_TREE_REMOVED`，
`remove` 之前置 1、rescan 结束时清 0，并注册四个 trap。

| 脚本 | 覆盖的 remove 点 |
|---|---|
| `b580-bar-tool.sh` | `apply` 主路径、`rollback_to` 回滚路径、`rehearse` 演练路径（共 3 处） |
| `tools/rebar-batch.sh` | 第 8 步 remove 锚点、回滚 remove 锚点（共 2 处）；额外记录 `ANCHOR_GONE` 与 `CARDS_EXPECT`，便于 trap 里判断"哪些卡该回来" |

| trap | 行为 |
|---|---|
| `INT` / `TERM` / `HUP` | 先清掉所有 trap，再补一次 `rescan`（单卡最多 4 次、每次间隔 1 秒；批量复用 `rescan_and_wait`），然后 `exit 130` |
| `EXIT` | 正常路径下标志为 0，立即返回；异常路径下补一次 `rescan` |

恢复成功打印 "PCI 子树已恢复"，失败则打印人工命令
（`echo 1 \| sudo tee /sys/bus/pci/rescan`）并提示"重启后先跑 `check`"。

**已知边界**：`SIGKILL`、OOM、断电、硬复位捕获不到，仍可能留下消失的子树。
所以 `check` 里的残留检测逻辑保留，作为这几种场景下唯一的补救线索。

**验证（两层）**：

1. **逻辑层** —— 把 trap 代码块原样抽出、仅把 `/sys/bus/pci` 替换为临时目录前缀，
   跑了 6 组共 11 项断言（标志为 0 时静默跳过 / GPU 回来后清标志 / GPU 不回时报错且不清标志 /
   给出人工命令 / `INT` 退出码 130 / 标志为 0 时不做多余 rescan），**11 项全部通过**。

2. **真机层**（2026-10-28 02:10，双卡机，目标 `0000:04:00.0` / 根端口 `0000:00:02.0`）：
   - 正常 `rehearse`：4 秒完成，BAR2 仍 16384MB，Control 仍 `00000e22`，**trap 完全静默**——
     确认不干扰正常流程。
   - `timeout -s TERM 1.8`（信号落在解绑与 remove 之间）：打了「已被中断」但**未做多余 rescan**，
     判定正确。
   - 在临时副本的 `remove` 之后注入 `sleep 5` 人为扩大窗口，再 `timeout -s TERM 3.5`：
     **打出「检测到中断发生在 remove 与 rescan 之间」→ 2 秒内恢复，`04:00.0` 回到 sysfs，
     `xe` 驱动自动重绑**。这是修复有效的直接证据。
   - 测试后三个推理服务（8094 / 8093 / 8092）全部恢复，rerank 实际推理返回正常排序。

**实测修正了一个判断**：真实 `remove → rescan` 窗口在本机是**毫秒级**（两者发生在同一秒内），
正常操作几乎不可能恰好打断在此处。所以这个 P0 的**实际触发概率远低于我们（和三席）原先的估计**。
保留修复的理由不是概率，而是代价极低且能防住 `remove` 卡顿与未来改动 — 详见 `NEXT.md`。

## 六、我们认为三席判偏的地方

这一节是留给后来者的"反对意见记录"，如果有人认为我们错了，可以直接从这里推翻。

**6.1「误伤其他 PCIe 设备」不是这套代码的弱点，而是它最强的部分。**
三席在这条上花了大量篇幅（嵌套桥、PCIe Switch、多张同型号卡共享根端口……），
但 `topo_subtree` 递归枚举整棵子树、遇未知 class **一律 fail-closed**，
`preflight_subtree` 又复查一遍。没有人找到能拆掉 NVMe 或系统盘的路径。
这是真正的技术资产，不该被当作风险点反复敲打。

**6.2 三席各报了"假成功"的一段，但没人把它们串起来。**
串起来之后是一个可复现的坏结局：某次开机在 remove 与 rescan 之间被 300s 超时掐死 →
从那天起每次开机自愈都"报 OK 但什么也没做" → `--check` 的报警在响，
但 `--check` 自己在零设备时又返回 0。**三条修法各 1 行，这是最该立刻改的东西。**
（已在 `9d48964` 修完，实测三档退出码 3 / 1 / 0 全部通过。）

**6.3 三席都漏、我们认为该补的：`set -uo pipefail` 但没有 `-e`。**
所以所有写入失败必须显式判断。第 12 步回滚的 `setpci ... && say "恢复"`，
失败时静默无声 —— 用户既看不到"恢复成功"，也看不到"恢复失败"。**已修**（回读比对 + rebind）。
