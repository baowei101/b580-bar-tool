## 两席共同指认、已修复的 5 处高危缺陷

提交 `6af0aa8`。以下均经代码核对确认成立：

1. **寄存器读空被当 0 → 假幂等成功。** `setpci` 失败返回空串，`hex2dec` 得 0，`0 >= 0` 成立，于是打印"已是目标尺寸"并**以退出码 0 退出**——什么都没做却报成功。两席分别列第 1、第 3 位。修法：新增 `assert_reg()`，读空或非十六进制立即 `die`。
2. **回滚判据 `bar2_mb > 0`。** GPU 一度不可见时写回被跳过，rescan 后仍按扩容值分配，却打印"回滚完成，BAR2=16384MB"。改为必须等于原始 size 对应的 MB。
3. **解绑失败仅 WARN 后继续 remove 根端口。** 带绑定驱动 remove 属内核 UAF 风险。改为失败上抛，`do_resize` 以返回码 3 中止（未做任何修改，无需回滚）；回滚路径仍放行（恢复原值是首要目标）。
4. **`subtree_devices ""` 枚举整机。** `realpath` 退化为 `/sys/bus/pci/devices`，前缀匹配命中全机，`unbind_leaf_drivers` 会解绑网卡/存储驱动。已加空值守卫。
5. **`cmd_rollback` 无状态文件时默认 N=8（256MB）**，比原始 N=9（512MB）更小。改为以当前值兜底并加幂等退出。

## 一处评审未能预见的事实

两席均按"根端口窗口只有 520MB、16GB 物理不可达"的既有前提推断风险等级。实际执行 `apply --size 10`（1GB 探针）后，**根端口窗口被全量 re-enumeration 从 520MB 扩到 1032MB**；随后 `--size 14` 扩到 16392MB，BAR2 成功拿到 16384MB，CPU 可访问显存达 11.9GB。

原因是 `pci_resize_resource()`（xe 驱动路径）只在现有桥窗口内找空间，而本方案走 `pbus_reassign_bridge_resources`，会重排并扩大桥窗口。这一点在评审阶段无法从静态代码得出，只能靠实测。
