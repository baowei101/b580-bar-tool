# 案例：双 B580 各占一个根端口（Xeon E5 v3 / C610 平台）

> **这份文档不是通用前提，只是一台具体机器的实测记录。**
> 通用逻辑在 `tools/lib/topology.sh` 里，正文所有结论都是探测出来的；
> 换主板后请重新跑 `tools/gpu-topology.sh --plan`，不要照抄这里的 BDF。

记录时间：2026-10-27（Linux 7.0.0，xe 驱动，pciutils 常规版本）

---

## 一、拓扑

两颗显卡各自挂在一个独立的根端口下，**不共享根端口**：

```
0000:00:01.0 [Port#1, Cap x16]  LnkSta x0   ← 空槽
0000:00:02.0 [Port#2, Cap x16]  LnkSta x8   ← 卡1
  └─ 0000:02:00.0 (8086:e2ff)  卡1 的内部桥     LnkSta x8 / 8GT/s
       ├─ 0000:03:01.0 (8086:e2f0) ── 0000:04:00.0  GPU 核心
       └─ 0000:03:02.0 (8086:e2f1) ── 0000:05:00.0  HDMI 音频
0000:00:03.0 [Port#7, Cap x16]  LnkSta x8   ← 卡2
  └─ 0000:06:00.0 (8086:e2ff)  卡2 的内部桥     LnkSta x8 / 8GT/s
       ├─ 0000:07:01.0 (8086:e2f0) ── 0000:08:00.0  GPU 核心
       └─ 0000:07:02.0 (8086:e2f1) ── 0000:09:00.0  HDMI 音频
0000:00:1c.2 [x1] ── 0000:0b:00.0  网卡
0000:00:1c.3 [x1] ── 0000:0c:00.0  网卡
0000:00:1f.2        系统盘 SATA（独立）
```

### 关键点 1：中间的"交换机"是显卡自带的

`8086:e2ff` / `e2f0` / `e2f1` 是 Intel Battlemage 卡内的 PCIe 桥与端口，
**不是外置转接卡**。所以从主板视角看，"一张卡"是 `02:00.0` 这么一个桥设备，
GPU 核心和 HDMI 音频都在它下面。

### 关键点 2：GPU 核心显示 x1 / 2.5GT/s 是正常的

```
0000:04:00.0  cur=1 / max=1 / 2.5 GT/s     ← 卡内链路，不是槽位链路
0000:02:00.0  cur=8 / max=8 / 8.0 GT/s     ← 真正的槽位链路
```

第一次看到 `max_link_width=1` 会以为"插错槽了/金手指坏了"，实际是读错了层级。
**判断插槽是否正常，看卡内桥（`e2ff`）的 `current_link_width`。**
B580 本身是 x8 卡，Gen3 则是这颗 CPU 的上限，两个都正常。

### 关键点 3：第二张卡不一定是"下一个总线号"

插卡前预期第二张是 `06:00.0`，实际是 `08:00.0` —— 因为卡内桥自己占用了总线 06，
把 GPU 推到了 07 段之后的 08。**BDF 无法预测，只能枚举。**

## 二、探测输出

```
BDF            ID          DRIVER   DRM                REBAR  BAR2      安全锚点  锚点窗口
-------------- ----------- -------- ------------------ ------ --------- ------------- ---------
0000:04:00.0   8086:e20b   xe       card0 renderD128   yes    512MB     0000:00:02.0  520MB
    能力   : ecap=0x420  支持档位: 256MB 512MB 1024MB 2048MB 4096MB 8192MB 16384MB
0000:08:00.0   8086:e20b   xe       card1 renderD129   yes    512MB     0000:00:03.0  520MB
    能力   : ecap=0x420  支持档位: 256MB 512MB 1024MB 2048MB 4096MB 8192MB 16384MB

锚点 0000:00:02.0   卡片数 1   当前窗口 520MB   需要 16384MB   策略 atomic
锚点 0000:00:03.0   卡片数 1   当前窗口 520MB   需要 16384MB   策略 atomic
```

- `ecap=0x420` 是**遍历扩展能力链表查出来的**，不是写死的。
  链路实测：`0x100` → `0x110` → `0x200` → `0x420`（第 4 项，Capability ID `0x0015`）。
- 安全锚点 = 根端口（这两个根端口下除了本卡没有别的设备），所以 `atomic`。
- 两卡各自要 16GB 窗口，**不存在"需要 32GB 单窗口"的问题** ——
  那是"两卡共享一个根端口"时才会出现的约束。

## 三、锚点为什么能升到根端口

按 `topo_subtree_safe` 的规则逐级检查（子树里除自己外只允许：桥 / 本工具目标卡 / 音频）：

| 候选锚点 | 子树内容 | 是否安全 |
|---|---|---|
| `00:02.0` 根端口 | `02:00.0` `03:01.0` `03:02.0` `04:00.0` `05:00.0` | ✅ 桥 + 目标卡 + 音频 |
| `02:00.0` 卡内桥 | `03:01.0` `03:02.0` `04:00.0` `05:00.0` | ✅ |
| `03:01.0` 下游口 | `04:00.0` | ✅ |

取最高的一级 → `00:02.0`。如果这个根端口上还挂着一块 NVMe，第一行就会判定为不安全，
锚点自动降到 `02:00.0`，**绝不会去摘别人的盘**。

## 四、这台机器上踩到的两个坑

| 现象 | 真因 |
|---|---|
| `status` 报"未找到带 ReBAR 的显示设备"，但 `topology.sh` 能读 `0x420` | 主脚本里写成 `[ "$capid" -eq "$ECAP_ID_REBAR" ]`，`[` 不认 `0x` 前缀 → 恒为假。改用 `(( capid == ECAP_ID_REBAR ))` |
| 计划里显示"锚点 0、本组 0 张" | 分组数组命名为 `GROUPS`，与 bash 保留变量冲突（root 的组 ID 就是 `0`）。改名 `ANCHOR_GROUPS` |

两个都不会报错，只会安静地给出错误结论 —— 所以探测层的输出必须逐项核对一遍再动手。

## 五、扩容实测（2026-10-28 00:50，两张卡逐张串行）

两步之间**没有任何并行**：脚本本体是阻塞 `for` 循环，第一张卡的 `apply` 完全返回后才进入第二张
（`grep '&$\|wait\|xargs -P\|parallel'` 在三个执行脚本里零命中）。

| 步骤 | 卡1 `0000:04:00.0` | 卡2 `0000:08:00.0` |
|---|---|---|
| 锚点 | `0000:00:02.0` | `0000:00:03.0` |
| 耗时 | 4 秒 | 4 秒（卡1 结束后才开始） |
| BAR2 | 512 → **16384MB** | 512 → **16384MB** |
| 锚点窗口 | 520MB → **16392M** | 520MB → **16392M** |
| Control `0x428` | `00000e22` | `00000e22` |
| 驱动 | `xe` 自动重绑 | `xe` 自动重绑 |

整机侧证：PCI 设备总数 197 → 197（未丢设备）；`05:00.0`/`09:00.0` 两个 HDMI 音频仍是
`snd_hda_intel`；两块 I210 网卡 `igb` 正常；`rebar-autofix.sh --check` 退出码 0。

SYCL 侧证：`level_zero:0` 对应 `04:00.0`、`level_zero:1` 对应 `08:00.0`；
两张 `max_mem_alloc` 均为 **11.33 GiB**（512MB BAR 时不可能超过 0.5GiB）；
16MB `malloc_device` + 核函数 + reduction 在两张卡上分别 PASS。

结论：**两个锚点确实互相独立**，"逐张 apply 会把另一张挤小" 这个共享根端口才有的问题在这台机器上不存在。
但换一台卡挂同一根端口下的机器，`topo_strategy` 会判成 `batch` 并要求一次性结算 —— 别把这里的结论当通例。
